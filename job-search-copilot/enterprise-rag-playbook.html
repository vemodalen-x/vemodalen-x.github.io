企业 RAG 不是“文档 + 向量库”

它是一条带身份、版本、出处、评测、发布门槛和运行观测的知识交付链路。目标是让员工拿到可引用、可解释、权限正确、能拒答的答案。

如何看待截图方案：它在多模态解析、混合召回、重排、上下文和 RAGAS 评测上方向正确。企业落地时，必须额外把 ACL / RBAC、文档版本与删除、来源定位、拒答、prompt injection 防护、线上观测和变更发布纳入硬门槛。

Reference architecture

从原始文档到受控答案的七层链路

向量数据库只是索引层。权限和 provenance 必须随内容进入每个 chunk，并在每一次查询中重新执行。

01 · CONNECT

源系统

SharePoint、Wiki、PDF/PPT、工单、数据库、对象存储；记录 owner、ACL、保留期。

02 · NORMALIZE

解析与规范化

OCR、layout/table/image extraction、页码/区域定位、去重、PII 与恶意内容扫描。

03 · GOVERN

内容契约

doc_id、version、parent/child、source URI、timestamp、ACL、sensitivity、parser version。

04 · INDEX

多索引

dense、BM25、metadata/ACL filter、parent-child、图像或表格索引；每项可回溯原文。

05 · RETRIEVE

身份检索

认证→权限过滤→query routing→hybrid recall→rerank→context packing。

06 · ANSWER

受约束回答

仅依据 evidence pack 作答，带出处与片段；证据不足时澄清、拒答或转人工。

07 · OPERATE

评测与运营

offline eval、canary、trace、反馈、freshness、ACL drift、成本/延迟和安全事件。

Non-negotiable gates

六个必须先答清的问题

技术选型排在这些设计门槛之后。没有它们，Recall@k 很高也不代表系统可部署。

GATE 01

什么内容可被回答？

  • 明确用户任务、风险等级和禁止自动化边界。
  • 先定义 source of truth、文档 owner 和过期规则。
  • 非权威、冲突或过期内容不能与正式规程等权处理。
GATE 02

权限如何端到端继承？

  • source ACL 在 ingestion 时进入每个 child chunk。
  • query 使用调用方身份；过滤发生在 retrieval 前。
  • ACL 变化、组成员变化和删除都有同步 SLA。
GATE 03

证据怎样可追溯？

  • 回答必须返回 doc、version、page/section、chunk 和检索时间。
  • 保留 parser、embedding、index、prompt、model 的版本。
  • 支持一键打开原文和 replay trace。
GATE 04

何时应该不回答？

  • 检索不足、证据冲突、权限不足或高风险行动时拒答。
  • 返回可操作的澄清问题、允许来源或人工路径。
  • 不能以流畅回答掩盖未知。
GATE 05

怎样评测再上线？

  • 把真实问题按设备、组件、文档类型、角色和难例切片。
  • 分开评测 retrieval、answer、citation、安全和系统性能。
  • 离线 gate → shadow/canary → 线上反馈闭环。
GATE 06

谁对变更负责？

  • 文件更新、ACL 更新、embedding/model 升级均可审计。
  • 定义 reindex、backfill、rollback、删除和 incident owner。
  • 指标下降、泄漏或 prompt injection 有 kill switch。
Implementation blueprint

把截图方案升级为可上线的设计

以“内网电力设备运维文档”为例；同样适用于企业流程手册、客服知识库、工程 Wiki 和合规文档。

层截图中的有效做法企业级补强验收证据
IngestionOCR 解析 PDF/PPT，抽取文字与图片。保留页码、layout、表格/图片区域、原文 URI、hash、parser version；对图片/表格设人工抽检和失败队列。解析成功率、字段完整率、页/区域可定位率、增量同步和删除演练。
Canonical content多模态图文向量。定义 parent-child chunks；每个 child 继承 doc/version/ACL/sensitivity；切分尊重章节和表格，避免跨文档拼接。chunk 质量抽样、父文档回链、ACL 继承测试、版本冲突测试。
IndexMilvus、dense/sparse、多层索引。维护 dense + lexical + metadata + ACL filter；图片/表格检索独立评测。向量、BM25、reranker 都以版本化 config 发布。每个 query slice 的 Recall@k、nDCG、filter 漏检/误放行率、index freshness。
Retrieve多路召回、BM25 + rules、BGE rerank。先从用户 token 获得 groups/roles，再做权限过滤；query router 只选合法语料域；rerank 后做 diversity、dedupe 和 context budget。权限测试集零泄漏；top-k 证据覆盖；p95、cost/query、空召回率。
AnswerQwen-VL / vLLM 生成。要求 citation、quote/span、版本日期；强制 evidence-only policy；证据不足/冲突时 clarification、abstention 或 human escalation。citation correctness、faithfulness、abstention precision、高风险任务的人工复核率。
MemoryRedis 管理长短期上下文。短期仅存 thread/task state；长期记忆与知识库分开，带 user/tenant namespace、TTL、PII/敏感写入检查；memory 不可绕过 ACL。跨租户隔离、过期删除、上下文污染、权限变化后 session replay。
OperateRAGAS 检索与答案指标。golden set + hard cases + online feedback；trace observability；文档/ACL/model/prompt/index 变更均可回放、canary 和 rollback。release scorecard、drift/incident alert、MTTR、业务任务完成率与人工接管。

  • hybrid recall + reranker + query routing。

应改变的表述

  • “多轮 memory”不是检索授权的替代品。
  • “准确率”须拆为 retrieval、grounding、citation 和任务成功。
  • “多模态 embedding”需要按图片、表格、扫描件分别验证。

必须新增

  • chunk 级 ACL、版本、删除和 sensitivity label。
  • prompt injection / data exfiltration threat model。
  • 拒答与人工升级，以及按版本的 canary/rollback。
Evaluation & operations

不要只看“回答像不像”

RAGAS 可以提供 useful signals，但不要把单一 LLM judge 分数当作上线真相。关键是使用经过人工审查的任务集、分层指标和线上守护指标。

OFFLINE GATES

发布前的五类指标

  • Retrieval：Recall@k、MRR/nDCG、evidence coverage、freshness、ACL leakage。
  • Answer：faithfulness、answer relevance、citation precision/recall、abstention correctness。
  • Multimodal：表格、图片、扫描件、图文组合的 groundedness 与 source localization。
  • Safety：prompt injection、越权检索、PII 泄漏、恶意文档污染和工具参数攻击。
  • System：p50/p95、cost/query、empty retrieval、index lag、error rate。
ONLINE GUARDRAILS

上线后持续看什么

  • 按用户角色、业务域、文档类型、query intent、版本和时间切片监控。
  • 记录 evidence pack、rerank、prompt、model、answer、citation、abstention 和人工接管 trace。
  • 报警：ACL sync 延迟、freshness 下降、citation 缺失、检索为空、异常成本、拒答激增或满意度急跌。
  • 更新文档、ACL、chunker、embedding、reranker 或 prompt 时先 shadow / canary，再推广。
一个更可靠的上线条件：高风险 query 的权限泄漏为 0；核心任务 slice 达到事先约定的 evidence coverage、citation 和任务成功门槛；遇到无证据/冲突证据时，系统能稳定拒答或升级，而不是更自信地编造。
Six-week delivery plan

先做窄而可靠的 MVP

不要一次接入 1200 份文档和全部 Agent 功能。选一个高价值、风险可控、owner 明确的工作流，建立可回归的基线。

WEEK 0–1

范围与数据契约

选 1 个核心任务和 2–3 类文档；确定 source of truth、ACL、保留期、风险等级、文档 owner；人工写 50–100 条 golden queries。

WEEK 2

可追溯 ingestion

先完成文本/PDF 的 parent-child chunking、metadata、version、ACL、source link 和删除路径；对 OCR 建失败队列。

WEEK 3

安全检索基线

实现 ACL filter → lexical+dense → rerank → evidence pack；把每一步记录为 trace，先不做复杂 multi-agent。

WEEK 4

引用与拒答

回答必须附 doc/page/section；无证据、冲突或高风险时澄清/拒答/升级；做 red-team 与权限测试。

WEEK 5

评测与多模态

建立 retrieval / answer / safety / system scorecard；只有在文本基线稳定后，再加入表格、图片与 VL extraction。

WEEK 6

Shadow → Canary

先对照人工流程，按用户/团队灰度；观察业务完成率、人工接管、成本、反馈和 ACL drift，保留 kill switch 与 rollback。

Sea interview / system design

5 分钟企业 RAG 白板回答

适用于“为企业设计知识助手”或“怎样让 RAG 上生产”的追问。先从用户与风险开始，而不是 LangChain、Milvus 或某个模型名。

“我会先把它建成 permission-aware knowledge delivery system，而不只是 chatbot。”

  1. 任务与边界：定义谁在什么工作流中需要何种答案，哪些内容是权威来源，哪些动作不可自动化。
  2. 内容链路：连接器保留 owner、ACL、版本、页码与 URI；解析 PDF/PPT/图表后生成 parent-child chunks，并把所有 provenance 继承到 child。
  3. 检索链路：调用方身份先获得 ACL filter；再按 intent 做 dense + lexical + metadata recall，rerank、dedupe 和 context packing，避免无权限 chunk 进入 prompt。
  4. 回答链路：模型仅依据 evidence pack 回答，返回 citation；证据不足、过期、冲突或高风险任务时澄清、拒答或转人工。
  5. 运营闭环：用真实任务集分别评测 retrieval、grounding、citation、安全、延迟和成本；所有 content/index/model/prompt 变更先 shadow/canary，异常可回放并 rollback。
